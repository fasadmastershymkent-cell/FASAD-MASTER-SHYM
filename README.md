# FASAD MASTER — сайт с общей базой

Эта версия сохраняет заказы, производство, рейсы, оплату, планы и чат через Supabase. Вход — по email и паролю. Сайт размещается на GitHub Pages; сотрудники на телефонах и компьютерах открывают одну ссылку. Обновление данных — каждые 10 секунд, пока страница открыта, и при возвращении в неё.

**Пока Supabase не настроен, синхронизация не работает.** В архиве нет чужой базы, готовых аккаунтов или секретных ключей. При пустом `config.js` сайт показывает настройку, а не демонстрационные заказы. Проверки ниже выполнены с локальной тестовой базой; публикация и проверка вашего облачного проекта ещё не выполнены.

Самый простой путь: подключите Supabase в этом чате и укажите ваш репозиторий или будущий адрес GitHub Pages. Тогда настройку проекта можно продолжить с уже подготовленными файлами. Пароли и секретные ключи присылать в чат не нужно.

## 1. Разместите файлы сайта

Распакуйте архив. Загрузите содержимое папки в корень репозитория GitHub. В корне должны лежать `index.html`, `app.js`, `style.css`, `config.js`, значки и `manifest.webmanifest`. Файлы в `setup/` понадобятся для базы.

В GitHub откройте **Settings → Pages → Deploy from a branch → main → / (root) → Save**. Скопируйте выданный адрес. Пример адреса: `https://YOUR-USERNAME.github.io/fasad/`. Это пример, не адрес уже опубликованного сайта.

[Официальная инструкция GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site).

## 2. Подключите общую базу один раз

1. Создайте отдельный проект в [Supabase](https://supabase.com/dashboard). Сохраните пароль базы у себя. Не загружайте его в репозиторий.
2. Откройте **SQL Editor → New query**. Вставьте весь файл `setup/database.sql` и выполните **Run**. Он создаёт общую таблицу с защитой от прямого доступа, атомарное сохранение и закрытое хранилище фотографий.
3. В **Edge Functions** создайте функцию с точным именем **fasad-api**. Замените содержимое `index.ts` целиком файлом `setup/index.ts` и опубликуйте функцию. В нём уже собраны необходимые зависимости.
4. Для этой функции установите **Verify JWT with legacy secret = OFF**. Это нужно для новых ключей Supabase и запросов браузера OPTIONS. Сама функция обязательно проверяет пользовательский токен через Supabase Auth при каждом обращении; данные без входа она не выдаёт. Не заменяйте её код пустым обработчиком без проверки.
5. В **Edge Functions → Secrets** добавьте `OWNER_EMAIL` — ваш email владельца и `ALLOWED_ORIGIN` — начало адреса GitHub Pages без пути и завершающего слеша, например `https://YOUR-USERNAME.github.io`. Для своего домена укажите его точное начало, например `https://app.example.kz`.
6. `SUPABASE_URL` и серверный ключ Supabase передаёт функции автоматически. Эти ключи не копируйте в файлы сайта. Если функция сообщает об отсутствии настроек, проверьте Secrets и журнал функции.
7. В **Authentication → URL Configuration** задайте **Site URL** и разрешённый **Redirect URL** равными полному адресу вашего сайта, например `https://YOUR-USERNAME.github.io/fasad/`. Здесь путь `/fasad/` нужен.
8. Откройте настройки ключей проекта. В `config.js` заполните только адрес проекта `https://...supabase.co` и **Publishable key** (`sb_publishable_...`) или старый **anon public key**. Сохраните файл в GitHub и дождитесь обновления Pages.

Пример формы файла — значения нужно взять из своего проекта:

```js
window.FASAD_CONFIG = {
  supabaseUrl: "https://ВАШ-ПРОЕКТ.supabase.co",
  supabaseKey: "ВАШ-ПУБЛИЧНЫЙ-КЛЮЧ"
};
```

**`service_role`, `sb_secret_...`, пароль базы и личный access token запрещено помещать в `config.js` или GitHub.** Публичный ключ не даёт доступа к заказам: вход и членство проверяет сервер.

[Публикация функций Supabase](https://supabase.com/docs/guides/functions/deploy), [адреса возврата после входа](https://supabase.com/docs/guides/auth/redirect-urls).

## 3. Создайте аккаунты и пригласите сотрудников

Для небольшой команды можно создать аккаунты вручную в Supabase: **Authentication → Users → Add user → Create new user**. Укажите email и пароль конкретного сотрудника, подтвердите этот аккаунт через административную настройку создания пользователя. Это действие владельца проекта. Не отключайте подтверждение email для всех регистраций.

Первый аккаунт владельца должен иметь подтверждённый email, в точности соответствующий `OWNER_EMAIL`. При первом входе он получает роль владельца. Данные начинаются с пустого рабочего пространства.

Войдите на сайте владельцем → **Команда → Создать приглашение** → выберите «Менеджер» или «Цех». Передайте сотруднику ссылку и код лично. Сотрудник входит в свой аккаунт, указывает имя и вводит код. Один код действует 7 дней; его можно отозвать. Создание аккаунта само по себе не открывает доступ к данным команды.

Для самостоятельной регистрации через «Создать аккаунт» и восстановления пароля настройте **Custom SMTP** в Supabase. Встроенная отправка почты ограничена адресами участников организации Supabase и не подходит для обычных сотрудников. **Не добавляйте сотрудников в администраторы Supabase ради получения писем.** Без SMTP используйте заранее созданные аккаунты; восстановление по письму не будет готово к работе. [Настройка почты Supabase](https://supabase.com/docs/guides/auth/auth-smtp).

## Проверка после подключения

Откройте сайт на двух устройствах с разными аккаунтами. Менеджер создаёт заказ на 100 м². Цех отмечает заливку и готовность. Менеджер создаёт первый рейс 60 м²: остаток клиенту должен стать 40 м². Второй рейс 40 м² закрывает остаток. Отметьте оплату, отправьте сообщение и добавьте план — они должны появиться на втором устройстве в течение 10 секунд. Перезагрузите обе страницы: записи должны сохраниться.

Владелец может выполнять действия менеджера и цеха. Менеджер не отмечает производство; цех не меняет оплату. При одновременном сохранении одного состояния система попросит повторить действие, сохранив чужие изменения. Повтор отправки после обрыва соединения использует тот же идентификатор операции.

## Если что-то не работает

| Что видно | Что проверить |
| --- | --- |
| «Общая база ещё не подключена» | Заполнен ли `config.js`, обновился ли GitHub Pages |
| «Этот адрес сайта не разрешён» | `ALLOWED_ORIGIN`: только протокол и домен, без имени репозитория |
| Ошибка функции / «Общая база пока не отвечает» | Функция называется `fasad-api`, опубликована, legacy JWT verification выключен, Secrets заполнены |
| «Для подключения нужен код» у владельца | Подтверждённый email аккаунта совпадает с `OWNER_EMAIL`; база ещё не принадлежит другому аккаунту |
| Письмо не приходит | SMTP, папка «Спам», адреса возврата; либо создание аккаунта владельцем через Users |
| Фото не загружается | Выполнен SQL, bucket `fasad-photos` закрытый, файл JPG/PNG/WebP до 4 МБ |
| Владелец видит изменения, сотрудник нет | Одинаковые сайт и проект Supabase, сотрудник состоит в команде, страница открыта и есть интернет |

Прямое открытие HTML с диска не предназначено для общей работы. GitHub размещает файлы сайта, Supabase хранит данные и проверяет доступ. Для сохранения нужен интернет. Значок приложения можно добавить через меню браузера; автономная работа без сети не предусмотрена.

- 35 проверок серверного подключения: токены, подтверждение email, владелец, запрет доступа посторонним, закрытые фото, ограничения запросов и ошибки сервиса.
- 20 проверок клиентского подключения, включая смену аккаунта во время обновления входа, ошибки настройки и путь репозитория GitHub.
- В браузере с локальной тестовой базой: два независимых аккаунта, создание заказа, заливка, готовность, рейсы 60 + 40 м², оплата, общий чат, план, сохранение после перезагрузки.

Тестовые аккаунты и тестовые заказы в архив не включены. Настоящий облачный проект, его SQL, доставку писем, работу с двух физических устройств через интернет и фактическую установку приложения нужно проверить после подключения.
